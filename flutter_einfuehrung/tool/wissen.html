1 · Was ist ein Widget?

In Flutter ist alles ein Widget: ein Text, ein Abstand, eine Farbe, ein Button, die ganze App. Ein Widget ist ein Bauplan für ein Stück Oberfläche. Es beschreibt, was angezeigt werden soll – Flutter kümmert sich darum, wie es gezeichnet wird.

Widgets sind unveränderlich Ein Widget-Objekt wird nie nachträglich geändert. Soll etwas anders aussehen, baut Flutter einfach ein neues Widget. Deshalb sind alle Felder eines Widgets final.
Widgets bilden einen Baum Jedes Widget kann Kinder haben (child oder children). Ganz oben steht das Widget, das Sie an runApp() übergeben – die Wurzel des Widget-Baums.

Die Frage ist nur: Woher kommen die Daten, die ein Widget anzeigt – und können sie sich ändern, während die App läuft? Genau darin unterscheiden sich Stateless und Stateful.

🖼 Stateless = gedrucktes Plakat Was draufsteht, wird beim Drucken festgelegt. Will man etwas anderes zeigen, druckt man ein neues Plakat.
🧑‍🏫 Stateful = Whiteboard mit Schreiber Das Whiteboard (Widget) bleibt hängen, aber eine Person (der State) merkt sich, was gerade gilt, und schreibt es neu an, sobald sich etwas ändert.

2 · Aufbau eines Stateless Widgets

Stateless heißt „ohne Zustand“. Das Widget zeigt nur an, was ihm von außen über den Konstruktor gegeben wird. Es kann sich nichts merken und sich nicht selbst neu zeichnen.

①class ToDoItem extends StatelessWidget {
②  final String title;

③  const ToDoItem(this.title, {super.key});

④  @override
  Widget build(BuildContext context) {
⑤    return Row(
      children: [
        const Checkbox(value: false, onChanged: null),
        Expanded(child: Text(title)),
      ],
    );
  }
}
  1. Klasse erbt von StatelessWidget. Damit weiß Flutter: Das ist ein Widget ohne eigenen Zustand. Klassennamen schreibt man in UpperCamelCase.
  2. Felder sind final. Die Daten (hier der Titel) werden einmal beim Erzeugen übergeben und nie mehr geändert.
  3. Konstruktor. this.title speichert den übergebenen Wert direkt im Feld. const erlaubt Flutter, gleiche Widgets wiederzuverwenden (schneller). {super.key} reicht einen optionalen Schlüssel an die Oberklasse weiter – brauchen Sie meist nicht, gehört aber dazu.
  4. build-Methode. @override heißt: Wir überschreiben die Methode der Oberklasse. Flutter ruft build auf, wann immer es das Widget zeichnen will. context sagt dem Widget, wo es im Baum steht.
  5. Rückgabe = Widget-Baum. build gibt immer genau ein Widget zurück – das darf beliebig viele Kinder haben.

Im Kurs: MyFirstApp (Level 1–3) und ToDoItem (Level 5–8) sind Stateless Widgets. Selbst wenn ein ToDoItem später abgehakt wird, bleibt es Stateless – den Haken bekommt es von außen (done).

3 · Aufbau eines Stateful Widgets

Stateful heißt „mit Zustand“. Ein Stateful Widget besteht immer aus zwei Klassen: dem Widget selbst (unveränderlich, wie oben) und einem State-Objekt, das sich Daten merkt und die Oberfläche baut.

Klasse 1: das Widget

①class MyLogin extends StatefulWidget {
②  const MyLogin({super.key});

③  @override
  State<MyLogin> createState() => _MyLoginState();
}

Klasse 2: der State

④class _MyLoginState extends State<MyLogin> {
⑤  String _username = '';
  bool _canLogin = false;

⑥  void _onChangedUsername(String text) {
    setState(() {
      _username = text;
      _canLogin = _username.isNotEmpty;
    });
  }

⑦  @override
  Widget build(BuildContext context) {
    return Column(children: [
      TextField(onChanged: _onChangedUsername),
      TextButton(
        onPressed: _canLogin ? () {} : null,
        child: const Text('Login'),
      ),
    ]);
  }
}
  1. Erbt von StatefulWidget. Diese Klasse ist genauso unveränderlich wie ein Stateless Widget.
  2. Konstruktor – wie beim Stateless Widget. Hier könnten auch final-Felder stehen, die von außen kommen (z. B. ein Titel). Im State liest man sie mit widget.titel.
  3. createState() ist die einzige Aufgabe dieser Klasse: Sie erzeugt einmal das passende State-Objekt. Es gibt hier keine build-Methode!
  4. Die State-Klasse erbt von State<MyLogin> – in den spitzen Klammern steht, zu welchem Widget sie gehört. Der Unterstrich _ macht sie privat: Nur diese Datei kennt sie.
  5. Zustand = normale Variablen (nicht final!). Sie bleiben erhalten, solange das Widget auf dem Bildschirm ist – auch wenn build hundertmal neu läuft.
  6. Methoden, die den Zustand ändern, tun das innerhalb von setState(() { … }). Das ist das Signal an Flutter: „Daten haben sich geändert – bitte neu zeichnen.“
  7. build liegt im State, nicht im Widget. Sie liest die Variablen und baut daraus die Oberfläche. Läuft sie nach setState neu, ist der Button plötzlich aktiv.

Tipp: In Android Studio und VS Code erzeugt das Kürzel stful + Tab beide Klassen auf einmal, stless ein Stateless Widget. Danach nur noch die Namen anpassen.

5 · Was macht setState genau?

1. EreignisNutzer tippt, klickt, gibt etwas ein
→
2. setState(() {…})Variable im State wird geändert
→
3. „schmutzig“Flutter markiert das Widget zum Neuzeichnen
→
4. build()läuft neu und liest die neuen Werte
→
5. Bildschirmzeigt den neuen Zustand
  • Ohne setState ändert sich zwar die Variable, aber Flutter erfährt nichts davon – build läuft nicht neu, der Bildschirm bleibt alt.
  • setState gibt es nur im State eines Stateful Widgets. Ein Stateless Widget hat keins.
  • Nur das Widget, dessen State sich ändert, und seine Kinder werden neu gebaut – nicht die ganze App.
  • Rufen Sie setState nie in build auf – das ergäbe eine Endlosschleife.

6 · Lebenszyklus eines Stateful Widgets

Ein State-Objekt durchläuft immer dieselben Stationen. Für die meisten Apps brauchen Sie nur build und setState – die anderen sind gut zu kennen.

createState()Widget kommt in den Baum – State wird einmal erzeugt
initState()einmalige Vorbereitung, z. B. Startwerte laden. Zuerst super.initState() aufrufen.
build()Oberfläche bauen – läuft oft
↺ setState() → build() … so oft wie nötig
dispose()Widget verschwindet (z. B. Seite geschlossen) – aufräumen, z. B. Controller schließen
@override
void initState() {
  super.initState();
  debugPrint('initState: einmal am Anfang');
}

@override
void dispose() {
  debugPrint('dispose: einmal am Ende');
  super.dispose();
}

Ausprobieren: Bauen Sie diese beiden Methoden in _MyLoginState ein und beobachten Sie die Konsole (Bonus-Aufgabe 6). Setzen Sie zusätzlich ein debugPrint('build') in build – wie oft erscheint es beim Tippen?

7 · Welches Widget nehme ich?

Muss sich das Widget selbst etwas merken, das sich ändert, während die App läuft (Eingaben, Haken, Liste, Zähler)?
Ja → StatefulWidgetDie veränderlichen Daten kommen als Variablen in den State, Änderungen immer mit setState.
Nein → StatelessWidgetAlles, was es anzeigt, bekommt es über den Konstruktor. Auch Funktionen (z. B. remove) kann man so übergeben.

Faustregel: So viele Stateless Widgets wie möglich, so wenige Stateful wie nötig – und den Zustand dort ablegen, wo er gebraucht wird. In der ToDo-App gehört die Liste in ToDoList (Stateful), weil dort hinzugefügt und gelöscht wird. Jedes ToDoItem bleibt Stateless und meldet Klicks über Funktionen nach oben.
